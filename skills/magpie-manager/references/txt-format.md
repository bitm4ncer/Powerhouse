# Kirby `.txt` Format — Conventions for Direct Edits

Magpie stores all content in flat Kirby `.txt` files. This reference covers the format details you need to make safe direct edits.

---

## Top-level structure

A `.txt` file is a sequence of fields separated by `----` (exactly 4 hyphens on their own line).

```
Field-Name: value

----

Other-Field: another value

----

Multi-Line-Field:

Content can span
multiple lines

----

Empty-Field: 

----
```

- **Encoding:** UTF-8 (no BOM)
- **Line endings:** Both LF and CRLF work; Kirby normalizes internally. On Windows MAMP, files are typically CRLF — preserve the existing line endings of the file you're editing.
- **Field names:** Kebab-case, first letter capitalized (`Builder-content`, `Page-custom-css`, `Custom-fonts`). Case-INsensitive on read but match the existing case for cleanliness.
- **Whitespace:** Empty line after value, then `----`, then empty line before next field name. There may be a single space after the colon when empty (`Field-Name: ` — that trailing space is fine).
- **Order:** Field order doesn't matter to Kirby (it reads by name). But by convention, panels write fields in tab order — keep the existing order to avoid confusing diffs.

## Value types in `.txt`

### Simple scalars
```
Title: Home
Year: 2024
Background-color: #f4efe7
Builder-active: true
Css-toggle: false
```

### Empty/null
```
Seo-title: 

Page-background-image: 
```
Just a trailing space (or nothing) after the colon means empty.

### Textarea / multi-line
```
Custom-css:

/* My custom CSS */
.my-class {
  color: red;
}
```
- Blank line after the `Field-Name:` line
- Then the value (which itself can contain blank lines)
- Then `----` to close

### Files / Pages (single or multiple)

Single file (still a list with one item):
```
Site-logo: 
 - file://abc123uuid
```

Multiple files:
```
Featured-image: 
 - file://uuid1
 - file://uuid2
```

Single page reference:
```
Anchor-page:
 - page://0YFjXXizqWY5FBQR
```

The space before `-` is **one space** (not two). The `file://` and `page://` prefixes are mandatory.

### Tags / multiselect
```
Category: Retail, Product Design, Wood
```
Comma-separated, single line.

### Structure (list of objects)

This is the trickiest type. Used for `Menu-items`, `Custom-fonts`, `Cv-data`, `Contact-items`, `Custom-links`, `Typography-overrides`, etc.

```
Menu-items: 
- 
  link_type: page
  link_page: 
    - page://0YFjXXizqWY5FBQR
  title: Work
  new_tab: false
- 
  link_type: anchor
  link_anchor: "#contact"
  title: Contact
  new_tab: false
```

Rules:
- Item separator: `- ` (dash + space) at indent level 0
- Sub-fields: indent level **2 spaces**
- Nested lists (e.g. `link_page` which is itself a files list): indent **4 spaces**, prefixed by `- `
- Strings with special characters (e.g. `#anchor`) — wrap in `"..."`
- Booleans: `true` or `false` (no quotes)
- Empty values: just the colon, no value

### Blocks / Builder-content (JSON)

The `builder_content` field is a single-line JSON array:

```
Builder-content: [{"attrs":{...},"columns":[{"blocks":[...],"id":"...","width":"1/1"}],"id":"..."},{...}]
```

- It's all on **one line** (no internal newlines in the JSON itself)
- JSON-encoded: `\n` for newlines inside text fields, `\"` for quotes inside strings, `\\` for backslash
- UUIDs throughout: `"id":"<uuid-v4>"` on section / column / block
- File refs inside content: `"image":["file://<uuid>"]`
- The line is long — Editor tools may show it wrapped, but it's one logical line

---

## Block JSON shape (inside `Builder-content`)

### Section
```json
{
  "attrs": { ... },          // section_bg_*, section_padding_*, etc.
  "columns": [ ... ],        // Array of columns
  "id": "<uuid>"             // Section UUID
}
```

### Column
```json
{
  "blocks": [ ... ],
  "id": "<uuid>",
  "width": "1/1"             // "1/1", "1/2", "1/3", "2/3", "1/4", "3/4", etc.
}
```

### Block
```json
{
  "content": { ... },        // Block-specific fields (see block-catalog.md)
  "id": "<uuid>",
  "isHidden": false,
  "type": "text"             // Block type identifier
}
```

The field order inside a block JSON varies (Kirby writes in alphabetical sometimes, sometimes blueprint order). Don't rely on order.

---

## UUIDs

- Format: standard UUID v4 (36 chars, `8-4-4-4-12` hex with dashes)
- Generated by the CLI for sections, columns, blocks when missing
- File UUIDs: shorter, e.g. `xn8c3ztssdvlapdf` (16 chars) — different format, generated by Kirby's media subsystem
- Page UUIDs: similar short format, e.g. `0YFjXXizqWY5FBQR`
- **Never invent UUIDs.** When adding via direct edit, copy them from existing blocks, or omit and use the CLI to add a new section.
- UUIDs are stable across edits — same block keeps its `id`

## File and Folder Naming (Kirby Pages on Disk)

```
content/
├── site.txt                       # site-level fields
├── 1_home/                        # page (prefix = sort order)
│   ├── home.txt                   # page content (filename = template)
│   ├── 1_stadt-laden/             # child page
│   │   └── project.txt            # uses 'project' template
│   └── images/                    # optional page-specific files (not used much; media-library is preferred)
├── 2_legal-notice-privacy/
│   └── legal.txt
├── error/
│   └── error.txt
└── media-library/
    ├── default.txt
    └── (all uploaded files)
```

### Folder Naming Rules
- **Numeric prefix** (`1_`, `2_`, …) sets sort order; the prefix is stripped from URL by Magpie's route
- **Slug** part is kebab-case, lowercase: `1_stadt-laden`, `2_legal-notice-privacy`
- **No prefix** = unlisted (draft) page

### File Naming Rules
- Filename = `<template-name>.txt`
- `home.txt`, `default.txt` → uses `default` template (or template `home` if `home.yml` blueprint exists)
- `project.txt` → uses `project` template
- `legal.txt` → uses `legal` template
- `error.txt` → uses `error` template

### Page identification
- Page ID (used by CLI `--page=<id>`) = the URL path WITHOUT prefixes:
  - `1_home/` → page id `home`
  - `1_home/1_stadt-laden/` → page id `home/stadt-laden`
  - `2_legal-notice-privacy/` → page id `legal-notice-privacy`
- Always verify with `php builder-cli.php list-pages` before destructive ops.

## Editing Existing `.txt` Surgical (without CLI)

### Pattern 1: Change a top-level scalar
Use the Edit tool with the **full surrounding context** to make the old_string unique:

```
old_string:
"
Accent-color: #7A8761

----
"

new_string:
"
Accent-color: #ff6b35

----
"
```

The surrounding `----` and blank lines make the match unique.

### Pattern 2: Toggle a flag
```
old_string: "Page-css-toggle: false"
new_string: "Page-css-toggle: true"
```
Be aware: if multiple `*-toggle` fields exist, include enough context to disambiguate.

### Pattern 3: Edit inside `Builder-content` JSON
Find a unique JSON substring around the field. Example — change a text block's `text` value:

The block's JSON contains: `"content":{"text":"Studio","text_align":"left", ...}`. Multiple blocks may share `text_align:left`, but `"text":"Studio"` is likely unique.

```
old_string: '"text":"Studio","text_align":"left"'
new_string: '"text":"About","text_align":"left"'
```

If `"text":"Studio"` appears multiple times, include surrounding context (e.g. the block's `id`).

### Pattern 4: Delete a block from `Builder-content`
This is destructive — backup first.

The block JSON looks like:
```
{"content":{...},"id":"<uuid>","isHidden":false,"type":"text"}
```
Surround with the comma that separates it from siblings. Include the preceding comma if removing a middle/trailing block:

```
old_string: ',{"content":{...},"id":"<the-uuid>","isHidden":false,"type":"text"}'
new_string: ''
```

For the first block in a column, remove the trailing comma instead. Validate after with:
```bash
$PHP $CLI get-builder --page=<id>
```
If the page errors, restore from backup.

### Pattern 5: Reorder blocks
Tricky — swap two block JSONs. Better: use `update-builder` with the reordered JSON.

### Pattern 6: Add a new block to an existing column
Use **CLI `append-section`** if it's a new section. To add a block to an *existing* column, the cleanest path:
1. `get-builder --page=<id> > .tmp/backup.json`
2. Read `.tmp/backup.json`, modify the column's `blocks` array in memory
3. Extract `raw` field, modify, write to `.tmp/modified.json`
4. `update-builder --page=<id> --content=@.tmp/modified.json`

Or do a careful Direct-Edit by finding the closing `]` of the column's `blocks` array and inserting before it — but that's brittle. Prefer CLI for structural changes.

## Validation tips before saving

For JSON-heavy edits to `Builder-content`:
1. Copy the new JSON to a tmp file
2. `php -r "json_decode(file_get_contents('.tmp/edit.json')); echo json_last_error_msg();"` — should print `No error`
3. Or use Python: `python -m json.tool .tmp/edit.json > /dev/null`

For structure YAML edits (Menu-items, etc.):
1. Make the edit
2. Reload the page in preview — if it 500s, the YAML is broken; restore from git/backup

Always `git diff` before saving to manually inspect.

## Multi-Language

Magpie supports Kirby's multi-language but **studio sites typically run single-language**.

When enabled:
- `content/site.de.txt`, `content/site.en.txt`, etc.
- `home/home.de.txt`, `home/home.en.txt`
- Default language file may omit the language suffix or use the primary code

Check `magpie-config/config/config.php` for `languages` setting before assuming multi-lang. If the project is single-language, do NOT create per-language files.
